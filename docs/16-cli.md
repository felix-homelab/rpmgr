# 16 — Command line

> Status: Phase 1 is implemented. Tags: [F] fact · [R] recommendation · [T] target · [V] verify
> at implementation ([README](README.md#how-to-read-these-documents)).
>
> This document lists every `rpmgr` command, its flags and its exit codes. It is written from the
> commands' `--help` output and changes in the same PR as the command. Configuration keys are in
> [10](10-operations.md#configuration); the API behind the resource commands is in [07](07-api.md).

## Conventions

- One binary, `rpmgr`, for every role and every administration task
  ([ADR-0002](adr/0002-one-binary-three-roles.md)). Commands form a tree:
  `rpmgr <command> [<sub-command>] [flags] [arguments]`.
- Flags may stand before, between or after the positional arguments. `--` ends the flags: every
  argument after it is positional, also one that begins with `-`, such as a directory in
  `rpmgr release import -- -new`. `-h` or `--help` prints the help of any command, also after its
  arguments; `rpmgr help <command> …` does the same. See [Help](#help) for the sections and topics.
- A command names a resource by its ID or by its name, in an argument as in a flag such as
  `--group`: `get`, `delete`, `update`, `enable`, `disable`, `drain` and `decommission` take
  either. A value that starts with the kind's ID prefix, such as `rt_` for a route, is an ID. A
  name names an active connector or gateway: a decommissioned one, whose name a new one may have
  taken, is named by its ID.
- A flag that may be repeated, such as `--policy` or `--label`, sets a list or map. An empty value
  adds nothing, so the flag given once with an empty value sets an empty one: `rpmgr update route
  --policy '' <id>` takes every access policy off the route.
- No secret is ever accepted as a command-line argument: tokens and passwords come from a file, an
  explicitly passed environment variable or a terminal prompt
  ([04](04-security.md#secrets-at-rest-and-in-logs)).
- Commands of the public API put the verb first, `rpmgr <verb> <kind>` (`get`, `list`, `create`,
  `update`, `delete`, …), so they never collide with the role commands or with the host's
  `rpmgr policy` ([D51](14-open-decisions.md#engineering)). They arrive with the resource API.
- With `-o yaml` or `-o json`, standard output carries the resources alone, so that a script can
  parse it; what a write command says about the change, such as "Created route …" or the steps that
  prove a domain, goes to standard error. With the default `-o table` both go to standard output.
- From v1.0.0, the JSON and YAML output and the exit codes below are stable within a major
  release: fields are added, never renamed or removed. The table output is for people and may
  change in any release, so scripts use `-o json` or `-o yaml`
  ([07](07-api.md#versioning-and-compatibility),
  [D115](14-open-decisions.md#engineering)).
- `rpmgr setup` asks in full-screen forms on a terminal at least 40 columns wide, and otherwise
  in plain prompts on standard input and output, which a pipe or a screen reader can answer; the
  token goes into a hidden field in the forms and comes from the terminal prompt of `rpmgr enroll`
  otherwise ([D73](14-open-decisions.md#engineering)).
- A change that needs a step-up ([04](04-security.md#human-authentication-and-sessions)) asks for it
  on the terminal when the API answers `STEP_UP_REQUIRED`: the authenticator or a recovery code, or
  the password of a user without a second factor. The stored token then steps up for 10 minutes
  ([D63](14-open-decisions.md#engineering)) and the change runs again.

| Exit code | Meaning |
|---|---|
| 0 | Success, or help was requested |
| 1 | The command ran and failed |
| 2 | Invalid command line (unknown command or flag, missing or unexpected argument), or the command is not available in this build |
| 3 | Only `rpmgr migrate`: the database has a migration this binary does not know, which a newer release applied; the root updater's rollback restores its backup on this code alone ([04](04-security.md#controllers-and-all-in-ones-over-the-air)) |

## Help

`rpmgr --help` ([D151](14-open-decisions.md#engineering)) lists the commands of the root in
sections, each sorted by name, then the topics:

| Section | Commands |
|---|---|
| Resources | The verbs of the public API ([D51](14-open-decisions.md#engineering)): `get`, `list`, `create`, `update`, `delete`, `enable`, `disable`, `drain`, `decommission`, `revoke`, `set`, `preview`, `verify`, `check`, `trust`, `upload`, `renew`, `remove`, `advance`, `pause`, `resume`, `cancel`, `logs` |
| This host | What works on the host it runs on: `setup`, `enroll`, `leave`, `handoff`, `status`, `diag`, `policy`, `backup`, `restore`, `migrate`, `ca`, `kek`, `user`, `release`, `systemd-unit` |
| Run a role | `controller`, `gateway`, `connector`, `all-in-one` |
| Session | `login`, `logout`, `version` |

A command that is in no section is listed last, under "Other commands"; the commands of the
tree all have one. `rpmgr help <topic>` prints the commands of one task in the order they are used,
across the verbs and across this host and the API, with a line each on what it is for. A command
of that name wins over a topic. The topics are `updates` (release check and import, the update of
the controller, easy and staged rollouts) and `hand-off` (`rpmgr handoff`, `systemctl reload`,
`install.sh --upgrade --restart`). A topic names only commands that exist; a test checks it.

A command may be hidden: it is not listed in its parent's help, but it runs, its own help
works and the generated CLI reference lists it. `rpmgr updater`, with `install` and `apply`, is
hidden: it is plumbing for the install scripts and `rpmgr-update.service`, and units on deployed
hosts call `updater apply`. A removed command answers `unknown command "<name>"` with the command
that replaces it, and exit code 2.

## Commands

The connector-only build (`cmd/rpmgr-connector`, [D119](14-open-decisions.md#engineering)) has
the commands that run on a connector host: `connector`, `setup` and `systemd-unit` for the
connector role only, `enroll`, `leave`, `status`, `diag`, `policy` and `version`. Its
`controller`, `gateway` and `all-in-one` print "not available in this build" with exit code 2;
the other commands are not in its tree.

A command marked *not yet* exists in the command tree and prints "not available in this build"
with exit code 2 until its implementation lands; one marked *Phase 2* is designed and not in the
command tree yet.
