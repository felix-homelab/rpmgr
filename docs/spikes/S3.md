# S3: Can the gateway multiplex TCP/443 and UDP/443 as designed?

Status: Done · Date: 2026-10-06 · Issue: #7 · Code: tag `spike/s3` (branch `tmp/s3-port-443-mux`
while running)

## Question and rule

From [13](../13-roadmap.md#phase-0--spikes): a ClientHello peek with real clients (headless
Chromium and Firefox, curl, Go; D38), including post-quantum key shares; SNI-based certificate
selection with `GetConfigForClient`; one quic-go listener serving `h3` and `rpmgr-tunnel/1`. Pass:
all clients routed correctly; peek within limits; both ALPNs served from one UDP socket. Decides
[03](../03-connections.md#port-443-multiplexing) and the S3 part of
[ADR-0004](../adr/0004-quic-default-transport-policy.md).

Rule, agreed before the run: if one quic-go listener cannot serve both ALPNs well, tunnels move to a
separate UDP port (gateway boot-file key `listen.tunnel_udp`).

## Setup

- Go 1.27.1 (`toolchain go1.27.1`), quic-go v0.63.0, `golang.org/x/crypto` v0.57.0 (`cryptobyte`);
  WSL2 kernel 6.18, Docker 29.8. The facts below were read at these versions (D39).
- `spikes/s3/` on the tag `spike/s3`: the peek (`cryptobyte`, and `crypto/tls` aborted in
  `GetConfigForClient` for comparison), the TCP/443 routing table, and an all-in-one test gateway:
  an in-process controller (agent, Reauth and UI names on one TLS stack), an HTTP engine with
  per-SNI certificates, the tunnel endpoint (mutual TLS, connectors only), and a TLS-passthrough
  backend that terminates TLS itself. UDP/443: one `quic.Transport` and one listener with
  `NextProtos = {"h3", "rpmgr-tunnel/1"}`, dispatching on the negotiated ALPN, with per-ALPN
  connection-window budgets.
- Real clients: Chrome for Testing 153.0.8010.12 and its `chrome-headless-shell` (Playwright 1.63.0
  image), Firefox 155.0 driven by `playwright-core` 1.63.0, curl 8.22.0 with OpenSSL 3.5.8, and Go's
  `crypto/tls` and quic-go. Every client reached every route on loopback, directly (one segment)
  and through a relay that delivers its bytes in ≤ 1448-byte segments 2 ms apart, as on a path with
  a 1500-byte MTU. Browsers ignored certificate errors, because the routing was measured, not their
  trust stores; the Go clients verified against the test CAs.
- Realistic names: trust domain `rpmgr-s3test01`, gateway ID `gw_01JA2Z8Q6W7Y3V9K4M5N6P7Q8S`.
- `spikes/s3/README.md` repeats every run: `go test -race`, a 60 s fuzz run of the parser, and

Findings the design now uses:

- A `Transport` takes one listener; a second `Listen` fails with "listener already set"
  [F quic-go v0.63.0 `transport.go:173-175,209`].
- `http3.ConfigureTLSConfig` sets `NextProtos` to `["h3"]`, also in configurations returned by
  `GetConfigForClient` [F quic-go v0.63.0 `http3/server.go:48-71`].
- `quic.Config.GetConfigForClient` sees only `RemoteAddr` and `AddrVerified`
  [F quic-go v0.63.0 `interface.go:103-105,189-197`], so transport parameters cannot differ per
  ALPN on one listener. TLS settings can: `tls.Config.GetConfigForClient` sees SNI and the offered
  ALPNs [F Go 1.27.1 `crypto/tls/common.go:444-478`], and quic-go passes the configuration through
  [F quic-go v0.63.0 `internal/handshake/tls_config_go127.go:14-24`]. Tunnels get mutual TLS with
  the gateway certificate, `h3` the route's certificate without a client-certificate request.
- `AllowConnectionWindowIncrease(conn, delta)` must not call methods of the connection
  [F quic-go v0.63.0 `interface.go:145-151`]; the accept loop registers each connection's ALPN, and
  the callback looks it up.
- Go 1.27.1 enables the hybrid groups X25519MLKEM768, SecP256r1MLKEM768 and SecP384r1MLKEM1024 by
  default, X25519MLKEM768 first [F Go 1.27.1 `crypto/tls/defaults.go:23-42`], and a client sends an
  X25519 share next to it [F Go 1.27.1 `crypto/tls/handshake_client.go:153-159`].
- `tls.ClientHelloInfo` has no key-share groups; the `cryptobyte` peek reports them, depends on no
  `crypto/tls` internals and never writes to the client. The `crypto/tls` variant works too, but
  only with a connection that swallows the alert it sends when aborting.
- quic-go v0.63.0 requires `go 1.26.0` [F quic-go v0.63.0 `go.mod:3`].

## Outcome

All criteria pass, so the rule is not triggered: one quic-go listener serves `h3` and
`rpmgr-tunnel/1` on UDP/443, and tunnels share port 443 by default. `listen.tunnel_udp` stays the
option for when tunnel transport parameters must differ from public HTTP/3, because that cannot be
done on one listener. The TCP peek uses `cryptobyte`. The tunnel row of the routing table is made
precise: only this gateway's own `<gateway-id>.gateway.<td>`, with ALPN `rpmgr-tunnel-h2/1`, reaches
the data session; any other name under `.gateway.<td>` is handled like an unknown SNI.
[ADR-0004](../adr/0004-quic-default-transport-policy.md) stays *Proposed* until S1; its
Verification section records this result.

Changed in the same PR: ADR-0004, [03](../03-connections.md#port-443-multiplexing) (port 443
multiplexing, post-quantum key exchange, QUIC parameters) and
[04](../04-security.md#controller-certificates).

## Not verified

- Real network paths: every run used loopback; segmentation came from the relay, and there were no
  middleboxes and no IPv6 run.
- Branded release builds: Chrome for Testing 153 and Playwright's Firefox 155 build were used,
  with the same TLS stacks as the releases.
- HTTP/3 from Firefox (the testing Alt-Svc mapping did not switch it to HTTP/3 with an ignored
  certificate error) and from curl (the image has no HTTP/3); `h3` was shown with Go and Chromium.
- Chrome for Testing in new headless mode loads pages but does not exit after `--dump-dom` in the
  container; its evidence is the gateway's record, and `chrome-headless-shell` printed the pages.
- Encrypted Client Hello beyond Firefox's GREASE extension, the WSS row (Phase 2), and the cost of
  the shared listener under real load (S1 and the release benchmarks).
