# S5: Do Ent + Atlas deliver the data model on both dialects with tenancy enforced in one place?

Status: Done · Date: 2026-10-06 · Issue: #9 · Code: tag `spike/s5`
(branch `tmp/s5-ent-atlas` while running)

## Question and rule

- **Method:** a subset schema (orgs, connectors, routes, targets) with composite foreign keys, an
  `OrgScope` privacy rule, migrations generated and linted for SQLite and PostgreSQL; check which
  Atlas features the Apache-2.0 community build provides.
- **Pass criteria:** cross-org access impossible through the store; migrations apply cleanly on
  both dialects.
- **Rule** (D18): Ent + Atlas, using only Apache-2.0 parts (Ent, the `ariga.io/atlas` Go library).
  If Atlas CLI features rpmgr needs are missing from the community build, migrations are generated
  through Ent's Go API. If Ent itself fails (privacy rules, composite foreign keys): bun.

## Setup

- Development machine (x86-64, Linux 6.18 under WSL2); S5 checks correctness, nothing is timed.
- Go 1.27.1; `entgo.io/ent` v0.14.6, its generator pinned as a `go.mod` tool;
  `ariga.io/atlas` v1.3.0; `modernc.org/sqlite` v1.60.1 (SQLite 3.53.4); `jackc/pgx` v5.11.0;
  PostgreSQL 18.6 and 16.15 in Docker; the Atlas CLI community edition built from the v1.3.0
  source.
- Schema: orgs, gateway_groups, connectors, routes, route_targets. Migration 2 adds
  `health_checks`, an optional composite key `route_targets (org_id, health_check_id)` and
  `routes.description`, so that SQLite has to rebuild existing tables.
- Code, commands and raw outputs: `spikes/s5/` on the tag, with a `README.md` for every run.
  The tests run with `-race` on SQLite and on each PostgreSQL version.

## Results

| Criterion | Result | Pass |
|---|---|---|
| One Ent schema, both dialects | One schema and one generated client; migrations generated per dialect through Ent's Go API (`schema.NewMigrate` + `NamedDiff`, replay mode); regenerating yields no plan, and migration 2 regenerates byte-identically | yes |
| Scope only from the authorization layer | `authz.OrgScope` has unexported fields and an unexported context key; an org scope needs a membership; the system scope needs a job name, a reason and a successful audit record; a forged context value is ignored | yes |
| Deny by default | Without a scope every query, count, get, create, update and delete is denied | yes |
| Cross-org access through the store | Org B with org A's IDs gets `NotFound` (not a permission error) for reads, updates and deletes, and nothing of org A changes; lists, counts, edge traversals and eager loading return only org B; bulk updates and deletes touch only org B; a create in org A is denied; only the system scope changes `orgs` | yes |
| Policy bypass | `privacy.DecisionContext(ctx, privacy.Allow)` skips every Ent policy, and policies allow when no rule decides [F ent v0.14.6 privacy/privacy.go:168-182,212-226]. Filtering therefore lives in an interceptor and a mutation hook, which ignore that decision; with it set, no scope still reaches nothing and org B still cannot touch org A | yes |
| Composite foreign keys | Ent declares only single-column keys. An Ent diff hook [F ent v0.14.6 dialect/sql/schema/atlas.go:291-296] rewrites the desired Atlas schema: `org_id → orgs(id)` everywhere, and `(org_id, x_id) → parent(org_id, id)` between org-owned tables, on the parent's `UNIQUE (org_id, id)` | yes |
| … enforced by the database | On both dialects, through Ent (also in the system scope) and with plain SQL, the database refuses: a target of org B on org A's connector, route or health check; moving a target or a connector with targets to another org; deleting a connector that still has targets | yes |
| Migrations apply cleanly | From empty, and incrementally with data (the data survives SQLite's table rebuild); a second run applies nothing; the live schema equals the Ent schema, and the comparison detects a missing composite key; same on PostgreSQL 16 and 18 | yes |
| Integrity and failure | An edited migration or an unlisted file is refused before anything runs (`ErrChecksumMismatch`); a failing file is rolled back and leaves no revision | yes |
| Lint | Community CLI `migrate lint` runs on both dialects with no diagnostics, and flags a `DROP TABLE` as destructive (DS102) | yes |
| Atlas community build | `migrate diff --to ent://` is a stub there: "ent:// scheme is not supported by the community version" [F atlas v1.3.0 cmd/atlas/internal/cmdext/cmdext.go:573,648-655]. `migrate hash` (same `atlas.sum` as the Go API writes), `validate`, `lint`, `apply`, `status` and `schema inspect` work | partly |

Findings that change the implementation:

1. **SQLite enforces no foreign key** unless every connection sets `PRAGMA foreign_keys = 1`. The
   store opens SQLite only with that pragma and refuses a connection without it.
2. **Atlas rebuilds SQLite tables** between `PRAGMA foreign_keys = off` and `= on` in the
   migration file, without `PRAGMA foreign_key_check`, and SQLite ignores that pragma inside a
   transaction (shown by a test at SQLite 3.53.4). The store therefore applies each file in a
   transaction on one pinned connection, switches foreign keys off around it, runs
   `foreign_key_check` before the commit, and rolls back on any violation.
3. **The binary applies migrations itself** with `ariga.io/atlas`'s executor and its own revision
   table; no CLI at run time. On PostgreSQL the revision table's schema must be named, or Atlas's
   "database is clean" check counts it [F atlas v1.3.0 sql/migrate/migrate.go:692-700].
4. **Two exceptions to composite keys:** `routes.gateway_group_id` (and later
   `port_allocations.gateway_group_id`) may point at a shared gateway group of the system org
   (D14), so it stays single-column; grants are checked above the database.
5. **Tooling:** generated query types have no untyped `WhereP`, so the interceptor uses Ent's
   generated `intercept` package, and a checkout without generated code generates in two passes.
   Ent v0.14.6's generator needs `golang.org/x/tools` raised (v0.51.0) to load packages with
   Go 1.27, and Ent requires a pre-release of `ariga.io/atlas`, so v1.3.0 must be pinned
   explicitly.

## Outcome

The rule applies as follows:

- **Ent passes** both criteria (deny-by-default scoping and composite foreign keys), so bun is not
  needed.
- **The Atlas CLI community build cannot read Ent schemas** (`ent://`). Migrations are therefore
  generated through Ent's Go API with the Apache-2.0 `ariga.io/atlas` library, as the rule
  foresees, and applied by the binary with Atlas's executor.
- The community CLI's `lint`, `validate` and `hash` work and may run in CI as a development tool;
  rpmgr never needs Atlas's proprietary build or an Atlas account.
- `privacy.DecisionContext` is banned outside `internal/store` by lint, like `.Reveal()`.

## Not verified

- The full schema: the spike covers six tables. The cross-tenant leak suite generated from the
  service registry, and the authorization interceptor above the store, come with Phase 1.
- PostgreSQL below 16; SQLite on other platforms than linux/amd64 (S8).
- Concurrent startup of two controllers migrating at once (the database lock of 06).
- Query cost of the org filter on large tables; nothing was timed.
- Atlas's proprietary build was not run; what it adds is known only from the community build's
  messages.
- Migration 1 was first generated with the `ariga.io/atlas` pre-release Ent requires, before the
  version was pinned. With v1.3.0 it replays without a plan, lints, applies and matches the Ent
  schema; it was not regenerated.
