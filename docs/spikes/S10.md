# S10: Can a restart hand the listening sockets to a new process without refusing a visitor?

Status: Done · Date: 2026-10-26 · Issue: #880 · Code: tag `spike/s10`
(branch `tmp/s10-socket-handoff` while running)

## Question and rule

- **Question** (VB-08, [13](../13-roadmap.md#verification-backlog)): can a gateway, an all-in-one
  and a connector hand their listening sockets (TCP, UDP, QUIC) and sessions to a re-executed
  binary under systemd, so that no new visitor connection is refused and open ones drain
  ([D127](../14-open-decisions.md#project-and-process))?
- **Rules** S-1 to S-7 with their pass criteria and fallbacks, agreed before the spike ran
  ([D150](../14-open-decisions.md#engineering)), are in
  [ADR-0022](../adr/0022-socket-hand-off-by-re-exec.md#verification): S-1 TCP by re-exec; S-2
  QUIC by generation-tagged connection IDs and a relay; S-3 `udp` routes through the relay; S-4
  connectors' sessions; S-5 the control session; S-6 the all-in-one's database; S-7 the facts.

## Setup

- **Prototype** in `spikes/s10/`: a model gateway with the hand-off of ADR-0022 (binary check,
  re-exec with inherited sockets, manifest, status pipe, descriptor checks, `sd_notify`), a
  visitor TCP port served through connector streams, a visitor UDP port (echo per flow), connector
  sessions over QUIC and over TCP, and UDP modes `relay` (the design), `pause` (the rule's fallback)
  and `norelay` (counterfactual). Model connectors move at once on `Drain`; on `auto` they race QUIC
  against TCP, TCP 300 ms later.
- **Hosts:** systemd 249 (Ubuntu 22.04) and 257 (Debian 13) in containers pinned by digest, the
  unit `Type=notify`, `NotifyAccess=all`, `ExecReload=s10 handoff`, run as a service user, the
  binary owned by root. The load ran in a second container on a Docker bridge network: 500 new
  visitor connections per second, 10 to 20 long-lived ones pinging every 100 ms, UDP flows every
  20 ms, a new short flow every second, 64 MiB bulk streams for throughput. Hand-off drain 20 s,
  readiness window 10 s, session wait 5 s.
- **Versions** (D39): Go 1.27.3, quic-go v0.64.1, modernc.org/sqlite v1.60.1; Docker 29.9.2 on
  WSL2, Linux 6.18.33.2, 20 cores. `spikes/s10/README.md` repeats every run; raw results in
  `spikes/s10/results/`.
- **Scenarios** on both hosts: A relay mode, 4 QUIC connectors; B two hand-offs in a row; C
  hand-offs that must fail; E quic-go on the plain socket (baseline); F pause mode, 3 connectors on
  `auto` and 1 pinned to QUIC; D (Debian only) no relay. Each run ended by killing the unit's main
  process.

## Outcome

- **S-1, S-5, S-6 passed**: the TCP hand-off by re-exec with inherited sockets stands, with the
  requirement from S-5 that the old process opens no further control session after its
  `Goodbye{superseded}`.
- **S-2 and S-3 failed**, so their first fallbacks apply: only the old process reads the UDP
  sockets until it exits; it keeps its QUIC sessions and serves every `udp` flow; the new process
  starts QUIC and the UDP routes then; connectors on `auto` move over TCP meanwhile. No connection
  ID is tagged and nothing is relayed, which also keeps quic-go's fast path between hand-offs, where
  the relay's wrapper would have cost about a third of it all the time.
- **S-4 failed for a connector pinned to `quic`** under S-2's fallback, so its fallback applies:
  the old process keeps accepting public connections until the new one has sessions of every
  connector the old one had, at the latest until it exits. With connectors on `auto` that is
  within a second; with one pinned to `quic` the old process serves until the hand-off drain ends
  and cuts what is still open then.
- **Documents changed:** ADR-0022 → Accepted with the fallbacks; 03 "Restarts with socket
  hand-off" (the switch, UDP and QUIC, the control session, the facts), the timeout table (relay
  row removed);
  13 (VB-08 resolved; S10 listed); 14 (D150 notes the outcome); 05 (no longer `[V]`).

## Not verified

- **S-5 and S-4's fallback in the model.** The model has no controller; S-5 rests on rpmgr's code
  and tests. The model's old process stopped accepting at the switch, so S-4's fallback, accepting
  until every connector has moved, was not run as its own mode; 17.10 and 17.8 test it.

- **The product.** The model is not rpmgr: its TCP data session dials back per stream instead of
  rpmgr's reverse HTTP/2, so it could not open streams on a draining TCP session (the closed
  connections in B and C); the slices test the real gateway (17.10, 17.4, 17.8).
- **The all-in-one's 503 window** covers the database's move only; the time its controller takes
  to start is measured in 17.5.
- **Hosts.** Containers on one WSL2 machine and a Docker bridge network, not a real LAN or the
  reference testbed; throughput numbers are relative and vary between runs (the relayed path on
  the 249 host was much slower than on the 257 host). A faster relay would not change the outcome:
  its wrapper costs quic-go's fast path between hand-offs too.
- **Privileged ports** were not used (the model listened on 9000 to 9003); inherited sockets keep
  their binding, so `CAP_NET_BIND_SERVICE` matters only for sockets the new process binds itself.
