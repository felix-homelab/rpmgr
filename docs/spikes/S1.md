# S1: Is QUIC (quic-go) or TLS + reverse HTTP/2 the better default transport, and by how much?

Status: Done (decided by D45, 2026-10-07) · Date: 2026-10-06 · Issue: #5 · Code: tag `spike/s1`

## Question and rule

- **Method** ([13](../13-roadmap.md#phase-0--spikes)): benchmark subset from
  [12](../12-testing-and-quality.md#benchmarks): RTT {1, 80} ms × loss {0, 1} %, 1 and 32 streams,
  CPU per Gbit/s, on the reference testbed (D30), with a direct connection as the reference (D34).
- **Pass criteria:** data sufficient to set the default transport policy; numbers recorded.
- **Rule** (D19): QUIC and TCP + h2 are compared head-to-head on four metrics — single-stream
  throughput, 32-stream goodput at 1 % loss, connection-setup latency p99 and CPU per Gbit/s; the
  default is the transport that wins more of the four; a tie keeps QUIC.
- **External part** (D37): only the reference testbed would have decided. The maintainer has no
  testbed hardware; on 2026-10-07 he replaced the rule instead (D45, below).

**How the rule is computed** (proposed with the harness and confirmed by the product owner on
2026-10-07, before the testbed run, [D43](../14-open-decisions.md#project-and-process); moot
since D45, and still printed by `cmd/s1/summarize.go` as information):

| Metric | Cells | Better |
|---|---|---|
| M1 single-stream throughput | 1 stream, loss 0 % (the condition of the target in [03](../03-connections.md#targets-t)), RTT 1 and 80 ms, up and down | higher |
| M2 32-stream goodput at 1 % loss | 32 streams, RTT 1 and 80 ms, up and down | higher |
| M3 connection-setup latency p99 | loss 0 %, RTT 1 and 80 ms, 1 000 connections/s | lower |
| M4 CPU per Gbit/s | gateway + connector CPU seconds per Gbit delivered, RTT 1 ms, loss 0 %, 1 and 32 streams, up and down | lower |

Each cell is the median of its repetitions. Per metric, the QUIC ÷ h2 ratios of all cells and of
all three testbeds (x86-64, arm64, Raspberry Pi 5 as connector) are combined by geometric mean,
oriented so that a value above 1 favours QUIC. A transport **wins a metric** when the mean favours
it by at least 5 %; otherwise the metric is a tie. The default is the transport with more wins; a
tie keeps QUIC. The 5 % margin keeps run-to-run noise from deciding; pooling the testbeds keeps one
platform from deciding alone.

## Setup

- **Harness** (`spikes/s1/`, README there): a minimal gateway and connector over QUIC (quic-go
  v0.63.0) and TLS 1.3 + reverse HTTP/2 (`golang.org/x/net` v0.59.0) with the parameters of
  [03](../03-connections.md#quic-parameters) and two TCP connections per gateway; one stream per
  public connection, `StreamOpen` sent without waiting, `StreamResult` before service bytes,
  half-close preserved; mutual TLS 1.3 with a test CA. Go 1.27.1, `CGO_ENABLED=0`.
- **Workloads:** goodput for 1 and 32 TCP connections in each direction, acknowledged end to end
  by the service; connection setup at 1 000 connections/s, open loop (connect, 32-byte echo).
- **Path:** netem on the gateway↔connector link only (half the RTT and the full loss rate per
  direction, queue limit raised so netem does not cap the bandwidth-delay product). "direct" is a
  plain TCP connection over that link from the gateway host to the service.
- **Dry run** (this machine): three containers on one WSL2 host (Linux 6.18, 20 CPUs) with Docker
  bridges, 3 repetitions, 10 s per throughput run, 5 s per setup run.

## Results

Dry run, 2026-10-06: 180 measurements, 0 failed connections; medians of 3 repetitions
(`results/docker-dryrun.{jsonl,md,meta.txt}` on the branch). **Not the reference testbed; these
numbers decide nothing (D37).**

| Cell | direct | QUIC | TCP + h2 |
|---|---|---|---|
| 1 stream, 1 ms, 0 %, up / down (Mbit/s) | 22 200 / 22 400 | 751 / 741 | 2 220 / 2 100 |
| 1 stream, 80 ms, 0 %, up / down (Mbit/s) | 48.5 / 368 | 176 / 170 | 340 / 337 |
| 32 streams, 1 ms, 1 %, up / down (Mbit/s) | 25 200 / 20 500 | 331 / 341 | 1 780 / 1 860 |
| 32 streams, 80 ms, 1 %, up / down (Mbit/s) | 114 / 86.9 | 4.22 / 4.21 | 4.63 / 4.49 |
| Setup p99 at 1 000/s, 1 ms / 80 ms (ms) | 2.81 / 165 | 3.18 / 82.1 | 2.98 / 81.5 |
| CPU per Gbit/s, 1 ms, 0 %, 1 stream up / down (CPU s) | — | 2.18 / 2.49 | 1.42 / 1.22 |

The rule computation on these numbers gives QUIC 0, TCP + h2 3 wins (M3 a tie). What the dry run
does show:

| Observation | Pass |
|---|---|
| The harness runs every cell for all three systems and both transports without a failed connection; the summary checks the targets and applies the rule | yes |
| Connection setup through a warm session takes 1 RTT on both transports where a direct connection takes 2 (TCP handshake, then the echo): no extra round trip per user connection ([03](../03-connections.md#performance-budget)) | yes |
| Under 1 % loss at 80 ms both transports reach about 4 Mbit/s for 32 user connections, a direct connection about 100 Mbit/s: a tunnel carries 32 user connections in 1 (QUIC) or 2 (TCP + h2) congestion-controlled flows, so random loss limits all of them together. Head-of-line blocking costs latency per stream, not aggregate goodput, so the target "QUIC ≥ 1.5 × TCP + h2 at 1 % loss" may not be reachable by either transport | observation |
| Direct upload at 80 ms reaches 48.5 Mbit/s against 368 Mbit/s download, an asymmetry of the Docker setup that is not explained; the testbed run will show whether it is real | open |

## Outcome

**The rule is replaced, not applied** ([D45](../14-open-decisions.md#engineering), product owner,
2026-10-07). Both transports stay first-class, and the default transport is a setting instead of a
benchmark result: the instance default `default_transport` (`auto` = QUIC first with happy eyeballs,
`quic`, `h2`; shipped as `auto`), overridable per connector and per route
([03](../03-connections.md#transport-selection)).
[ADR-0004](../adr/0004-quic-default-transport-policy.md) is *Accepted* with that decision. The dry
run above favoured TCP + h2 on one shared host; it informs, it does not decide.

The harness becomes the benchmark suite of [12](../12-testing-and-quality.md#benchmarks) in
`bench/` (D36); it measures both transports against a direct connection before every release. The
deprioritisation of sessions with blocked stream writers, which S1 was to observe, is VB-18 in
[13](../13-roadmap.md#verification-backlog). Facts checked for the harness at the pinned versions
(D39):
quic-go v0.63.0 requires `go 1.26.0` [F quic-go v0.63.0 go.mod:3], where 08 states 1.25 for
v0.61; `Stream.Close` still closes only the send direction
[F quic-go v0.63.0 stream.go:192]; x/net v0.59.0 takes the HTTP/2 client's receive windows only
from net/http's `HTTP2Config` (`MaxReceiveBufferPerConnection`, `MaxReceiveBufferPerStream`) of the
wrapped `http.Transport` [F x/net v0.59.0 http2/config.go:88,150-155].

## Not verified

- The reference testbed (x86-64, arm64, Raspberry Pi 5) never ran; D45 made it unnecessary for
  Phase 0. The run sheet in `spikes/s1/README.md` serves the release benchmarks.
- The dry run shares one kernel and its CPUs among all three hosts, runs with 4 MiB UDP socket
  buffers (the host's limit; quic-go asks for 7 MiB and the limit cannot be raised per container),
  and its veth links are far faster than any NIC, so its numbers only show that the harness works.
- Not modelled by the harness: session control streams, `OpenRequest`, UDP datagrams, the window
  budget and happy eyeballs; they do not change TCP-route throughput, setup latency or CPU per byte.
