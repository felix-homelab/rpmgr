# S8: Does pure-Go SQLite cover the controller's platforms?

Status: Done · Date: 2026-10-06 · Issue: #12 · Code: tag `spike/s8`; native arm64 run: tag
`spike/s8-arm64`

## Question and rule

- **Method:** current `modernc.org/sqlite` on linux/amd64, arm64, armv7 and riscv64: test suite,
  WAL, `VACUUM INTO`. Where no hardware is at hand, QEMU user-mode emulation counts (D38); arm64
  and armv7 are run again on real hardware, a GitHub-hosted arm64 runner instead of the Raspberry
  Pi 5 ([D46](../14-open-decisions.md#project-and-process)).
- **Pass criteria:** the tests pass on the supported platforms; unsupported ones are documented.
- **Rule** ([ADR-0011](../adr/0011-sqlite-postgres-ent-atlas.md), agreed before the spike): the
  controller ships only on platforms that pass; the others are documented as unsupported.

## Setup

- x86-64 host, 20 logical CPUs, Linux 6.18 (WSL2), Docker 29.8. Go 1.27.1, `CGO_ENABLED=0`,
  `GOARM=7` for armv7.
- `modernc.org/sqlite` v1.60.1 with SQLite 3.53.4 [F modernc.org/sqlite v1.60.1
  `lib/sqlite.go:4556`] and `modernc.org/libc` v1.77.1. The driver requires `go 1.26.0`
  [F modernc.org/sqlite v1.60.1 `go.mod:3`].
- amd64 natively; arm64, armv7 and riscv64 under QEMU 10.0.13 user mode (`qemu-user-static` in a
  Debian 13 container, as an unprivileged user). The binaries are started explicitly with the
  emulator, so the host's `binfmt_misc` was not changed.
- Two test sets, built with `go test -c` for each target (`spikes/s8/run.sh`):
  1. **The driver's own test suite**: 159 top-level tests of `modernc.org/sqlite`.
  2. **The controller's use of SQLite** (06): a schema subset with composite `(org_id, id)` foreign
     keys and the `config_seq` counter (03); a DSN that sets every pragma on every pooled
     connection; one writer connection and a read-only pool.
- Port status at Go 1.27.1: linux/amd64, arm and arm64 are first-class ports, linux/riscv64 is not
  [F Go 1.27.1 `go tool dist list -json`]. The driver's builders test all four
  [F modernc.org/sqlite v1.60.1 `builder.json:5`].

## Results

**The driver's test suite** (top-level tests; durations of the main run):

| Platform | Passed | Skipped | Failed | Duration |
|---|---|---|---|---|
| linux/amd64, native | 157 | 2 | 0 | 492 s |
| linux/arm64, QEMU | 156 | 2 | 1 (`TestSEHTruncatedShm`, emulator) | 630 s |
| linux/arm (armv7), QEMU | 156 | 2 | 1 (`TestSEHTruncatedShm`, emulator) | 647 s |
| linux/riscv64, QEMU | 157 | 2 | 0 | 722 s |
| linux/arm64, native on Arm Neoverse-N2 (2026-10-07) | 157 | 2 | 0 | 500 s |
| linux/arm (armv7), native on the same host | 157 | 2 | 0 | 489 s |

- The two skips are the same everywhere and by the suite's design: one needs the build tag
  `memory.counters`, one must run before any other test in a process.
- **`TestSEHTruncatedShm` under QEMU arm and aarch64.** The test truncates the `-shm` file under
  the live mapping. The driver then recovers from SIGBUS only if the fault address lies in the
  wal-index pages. A probe (`spikes/s8/cmd/sigbusaddr`) shows that QEMU's arm and aarch64 user
  mode deliver this SIGBUS without the fault address, while amd64 natively and QEMU riscv64 report
  it correctly. The failure is the emulator's, not the driver's. In this scenario (another process
  truncating SQLite's shared-memory file) every non-Windows build of SQLite used to crash; the
  driver's recovery is an addition [F modernc.org/sqlite v1.60.1 `lib/seh.go:7-11`].
- **Adapted under emulation.** Five OFD-locking tests re-execute the test binary, which QEMU user
  mode cannot do without `binfmt_misc`; they ran directly in the child mode they re-execute into,
  and passed. `TestConcurrentGoroutines` ends with a `go test -race` re-run, which needs a Go
  toolchain; it ran with the suite's `-inner` flag, which skips only that step (amd64 ran it:
  PASS).
- **`TestIssue118`** (a heap-profile sampling check) failed once in the first arm64 run and in 1 of
  10 separate arm64 processes; 10 of 10 passed on the other platforms. Both failures are the same
  single sample: Go's one-time copy of the environment, made while `libc.NewTLS` builds `environ`
  during package initialisation [F modernc.org/libc v1.77.1 `libc_musl.go:295-297`]
  [F Go 1.27.1 `syscall/env_unix.go:30-32`]. It is a false positive of the check, not a
  per-connection leak, which would show in every run of its 10 000 connections.

**The controller's use of SQLite** (`spikes/s8/store_test.go`, `crash_test.go`):

| Criterion | amd64 | arm64 | armv7 | riscv64 |
|---|---|---|---|---|
| WAL, `busy_timeout`, `foreign_keys` and `synchronous` (FULL and NORMAL) on every pooled connection | pass | pass | pass | pass |
| One writer, 8 concurrent readers: each read transaction sees one snapshot of whole commits; readers never blocked | pass | pass | pass | pass |
| `busy_timeout`: a second writer waits, then gets `SQLITE_BUSY`; succeeds when the lock is released in time | pass | pass | pass | pass |
| 16 goroutines over two writer pools: `config_seq` revisions unique and gap-free; failed transactions leave nothing | pass | pass | pass | pass |
| Writer killed (SIGKILL) inside a ~20 MiB uncommitted transaction spilled into the WAL, and during a checkpoint: `integrity_check` ok, every reported commit present, nothing uncommitted | pass | pass | pass | pass |
| `VACUUM INTO` under write load: a consistent copy that opens, passes `integrity_check` and serves as a controller database; refuses an existing target and a missing directory | pass | pass | pass | pass |
| Composite foreign keys: cross-org insert and update refused; `RESTRICT`, `CASCADE`, `NOT NULL` | pass | pass | pass | pass |
| Invalid input: unknown DSN options, a missing directory, a file that is not a database | pass | pass | pass | pass |

Findings that change how Phase 1 uses the driver:

- By default a `_pragma` value in the DSN runs everything after a `;` as well; `StrictPragmas(true)`
  rejects such a DSN and is off by default [F modernc.org/sqlite v1.60.1 `strictpragma.go:20-43`].
- SQLite reports an `ON DELETE RESTRICT` violation with the extended code
  `SQLITE_CONSTRAINT_TRIGGER` (1811), not `SQLITE_CONSTRAINT_FOREIGNKEY` (787).
- `VACUUM INTO` fails on a `query_only` connection (`SQLITE_READONLY`); it needs an ordinary
  connection, but takes no write lock.

## Outcome

All four platforms pass. The rule therefore documents no platform as unsupported for SQLite
reasons: the controller may ship on linux/amd64, arm64, armv7 and riscv64. Their support levels
stay as in [05](../05-features.md#platform-support) (armv7 and riscv64 best effort, D29); S8 only
removes SQLite as a reason against them.

[ADR-0011](../adr/0011-sqlite-postgres-ent-atlas.md) records the result; with S5 also passed it is
*Accepted*. Updated in the same change: 14 (ADR status), [05](../05-features.md#platform-support),
[06](../06-data-model.md#database-engines) (connection settings, `StrictPragmas`, error codes,
`VACUUM INTO`), [08](../08-software-stack.md) (Go directive, Data row) and
[10](../10-operations.md#backup-and-restore).

## Not verified

- **Real hardware.** arm64 and armv7 ran natively on a GitHub-hosted arm64 runner (Arm
  Neoverse-N2, 4 vCPUs, Linux 6.17; D46): the driver suite and the spike's own tests pass on both,
  `TestSEHTruncatedShm` included, which confirms that its failure under QEMU was the emulator's
  (`results/hw-arm64/` on the tag `spike/s8-arm64`). No Raspberry Pi and no riscv64 hardware were
  available: riscv64 ran only under emulation, and its support stays best effort.
- **Power loss.** The crash tests kill the process; they do not cut power or crash the kernel, so
  the durability difference between `synchronous` FULL and NORMAL was not measured.
- **Performance.** Emulated timings say nothing about real hardware, and no throughput target was
  part of S8.
