# S6: Can certmagic run on the controller with database storage while gateways answer the challenges?

Status: Running (local part done; external run pending, D37) · Date: 2026-10-06 · Issue: #10 ·
Code: branch `tmp/s6-acme-certmagic` (commit `7099699`), tag `spike/s6` once this is merged

## Question and rule

From [13](../13-roadmap.md#phase-0--spikes): Pebble, then Let's Encrypt staging. HTTP-01 and
TLS-ALPN-01 answered by a gateway; DNS-01 through rpmgr's libdns adapter over the Cloudflare
client (fake Cloudflare API with Pebble, then a real test zone with staging), with a second
certmagic configuration for HTTP-01/TLS-ALPN-01 on the same storage, chosen per name; locking with
two controllers. **Pass:** certificates issued and renewed for both kinds of names, including a
wildcard; no duplicate orders under concurrency. **Rule (D17):** certmagic on the controller; if
gateway-answered challenges cannot work with certmagic, acmez with rpmgr's own solvers and
storage.

## Setup

- WSL2 (Linux 6.18, x86-64), Go 1.27.1. certmagic v0.25.6, acmez v3.1.7, libdns v1.1.1, Pebble
  v2.10.1 (in-process, ECDSA, chain length 1), modernc.org/sqlite v1.60.1, miekg/dns v1.1.73.
- Controller: certmagic with a `certmagic.Storage` on SQLite (`acme_storage`; locks as rows of
  `leases` with holder, expiry, fencing token, renewed while held). Gateway: answers HTTP-01 and
  TLS-ALPN-01 only from challenges pushed to it, serves pushed certificates, never reads the
  database and does not import certmagic. DNS-01: libdns adapter over a minimal Cloudflare client
  against a fake Cloudflare API, whose TXT records a small authoritative DNS server serves to
  Pebble's validator.
- Pebble validates for real (`PEBBLE_VA_ALWAYS_VALID` unset): it resolves names through the test
  DNS server and connects to the gateways' ports; `PEBBLE_AUTHZREUSE=0` makes every renewal
  validate again. The two-replica tests run the controllers as two **OS processes** on one SQLite
  file, because certmagic keeps process-global state (a job manager that deduplicates renewals by
  name) that would hide duplicates between replicas in one process.
- Commands and raw outputs: `spikes/s6/README.md` and `spikes/s6/results/` on the branch.

## Results

**How gateways answer.** certmagic v0.25.6 accepts a custom solver only for DNS-01; HTTP-01 and
TLS-ALPN-01 use its built-in solvers [F certmagic v0.25.6 acmeclient.go:188-226]. Those are
wrapped in its "distributed solver", which stores the challenge, key authorization included,
under `<issuer>/challenge_tokens/<name>.json` before the solver returns, and deletes it in
`CleanUp` [F certmagic v0.25.6 solvers.go:634-683]; acmez asks the CA to validate only after
`Present` returned. A storage decorator therefore pushes each stored challenge to **every gateway
that serves the name** and returns only when all acknowledged; a failed push fails `Present`, so
the CA is never asked to validate a challenge no gateway knows.

| Criterion | Result | Pass |
|---|---|---|
| HTTP-01 answered by a gateway | Issued; the gateway answered 3 validation requests per challenge (Pebble validates more than once); the certificate chains to Pebble's root and the gateway serves it after the push | yes |
| TLS-ALPN-01 answered by a gateway | Issued; 3 validation handshakes answered with the `acme-tls/1` certificate | yes |
| Negative controls | Without the push, validation fails at the CA (`unauthorized`), the gateway answers nothing; with one of two gateways not acknowledging, issuance fails and the CA receives **no** validation request; with two gateways, each answers when DNS sends the CA to it | yes |
| DNS-01 with a wildcard, fake Cloudflare | `apps.managed.test` and `*.apps.managed.test` issued; TXT records created with the marker comment and all deleted afterwards; no challenge pushed to gateways; a token the API rejects fails cleanly and leaves nothing | yes |
| Two configurations, one storage, chosen per name | Names in a managed zone (and every wildcard) use the DNS-01 configuration, all others HTTP-01/TLS-ALPN-01; one certificate cache picks the configuration by name, so renewals keep their challenge type; a wildcard outside a managed zone is refused before any order | yes |
| Renewal of both kinds | 40-second certificates: DNS name, wildcard and HTTP name renewed, each validating again (new TXT records, new pushes) | yes |
| No duplicate orders, two controller processes | 4 names obtained by both processes at once: exactly 1 order per name at the CA, both hold the same certificate, 7 lock acquisitions waited for the other process. The `[F]` facts on certmagic in [08](../08-software-stack.md#networking) and
[15](../15-dns.md#acme-dns-01) were re-checked at v0.25.6, the version already listed in the
README: the libdns interfaces (solvers.go:589-592), the 2-minute propagation default
(solvers.go:532) and "DNS-01 disables the other challenges" (README.md:408-422) are unchanged.

Observations:

- **Reliance on a certmagic internal.** The challenge key layout is not a documented API. A Phase 1
  test must pin it (the spike's end-to-end tests fail if it changes), and every certmagic upgrade
  runs that test.
- **ARI with very short certificates.** With ARI enabled, a replica that loads a just-renewed
  certificate whose CA-selected renewal time is already past renews it again
  (`results/raw/renew-ari-duplicate.txt`). Pebble's ARI window for a 40-second certificate starts
  at issuance [F Pebble v2.10.1 core/types.go:258-272]; real windows start days later. The
  two-process renewal test therefore disables ARI. Reading certmagic's renewal check also shows
  that an improvised ARI time is not used for the cutoff, which then lies at the zero time
  [F certmagic v0.25.6 certificates.go:125-146]: a stored window without a selected time renews
  at once. Not triggered in the runs; worth reporting upstream.
- **SQLite opened by two processes.** `busy_timeout` must be the first pragma in the DSN, and
  initialising a new database can return `SQLITE_BUSY` without the busy handler while another
  process switches it to WAL (`results/raw/rehearsal-sqlite-busy.txt`); a bounded retry fixed it.
  This matters for any second process on the controller's SQLite file, such as admin CLI commands.
- **Fencing.** certmagic does not pass the lease's fencing token to its storage writes, so a
  replica that lost its lease mid-order could still write a certificate. The effect is bounded to
  an extra order for the same name.

## Outcome

**Provisional, not yet applied (D37):** gateway-answered challenges work with certmagic through
its distributed-solver storage hook, so the rule keeps **certmagic on the controller**; acmez is
not needed. The rule is applied, this spike set to *Done* and the remaining `[V S6]` tags
resolved after the maintainer's run against Let's Encrypt staging and a real Cloudflare zone
(run sheet: `spikes/s6/README.md`, "External run").

Changed in this PR, for what the local run showed:
[04](../04-security.md#controller-certificates) (how route certificates are obtained),
[06](../06-data-model.md#pki-and-acme) (leases), [08](../08-software-stack.md#networking),
[12](../12-testing-and-quality.md#end-to-end-topology-matrix) (Pebble as the local ACME test
server) and [15](../15-dns.md#acme-dns-01) (two configurations, one cache).

The agent protocol had no message that pushes an ACME challenge to a gateway and returns its
acknowledgement. On the spike's recommendation the product owner added one on 2026-10-07
([D41](../14-open-decisions.md#engineering)): `ControllerMessage.AcmeChallenge{op_id, add | remove,
type, identifier, token, key_authorization}`, answered by `AgentMessage.OpResult`, sent to every
gateway of the name's gateway group with a deadline ([03](../03-connections.md#service-sketch)).
