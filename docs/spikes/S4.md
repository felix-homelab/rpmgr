# S4: Does ConnectRPC carry the agent control session?

Status: Done · Date: 2026-10-06 · Issue: #8 · Code: tag `spike/s4` (branch `tmp/s4-connectrpc`
while running)

## Question and rule

From [13](../13-roadmap.md#phase-0--spikes): a bidirectional stream over `net/http` HTTP/2 with
mutual TLS: cancellation, deadlines, message-size limits, HTTP/2 PING liveness, 10 000 concurrent
idle sessions (memory), behaviour behind a TLS-passthrough route. Pass: all behaviours correct;
memory per idle session recorded. Decides [ADR-0010](../adr/0010-connectrpc.md) and D20.

Rule, agreed before the run: ConnectRPC if every check passes; otherwise grpc-go for the agent
protocol only; browsers and the CLI stay on ConnectRPC.

## Setup

- Go 1.27.1, connect-go v1.21.0, protobuf-go v1.36.12, grpc-go v1.84.0 (the fallback, for
  comparison), x/net v0.59.0; buf v1.73.0. The facts below were read at these versions (D39).
- `spikes/s4/` on the tag `spike/s4`: a reduced `rpmgr.agent.v1.Control` service; a connect-go
  handler on `net/http` (TLS 1.3, mutual TLS against a test CA, HTTP/1.1 and HTTP/2, SNI
  `controller.<td>`); agents as connect-go clients speaking the gRPC protocol over an HTTP/2-only
  transport; a TCP relay that routes by SNI without terminating TLS and can blackhole a path; the
  same cases on grpc-go; `cmd/idle` for 10 000 sessions with the controller in its own process.
- One laptop (i7-1370P, 20 threads, 32 GB, WSL2 kernel 6.18), loopback only; other spikes ran at the
  same time, so CPU figures are indicative. `go test -race -count=1 -v ./...` repeats the tests
  (about 55 s); the spike's README has the real-value and 10 000-session runs.

## Results

| Criterion | Result | Pass |
|---|---|---|
| 1 Bidirectional streaming | 2 000 × 32 KiB in each direction at the same time, in order; more than the flow-control windows hold, so neither side finishes alone. Half-close: the server reads EOF and keeps sending | yes |
| 2 Cancellation | A cancelled client context ends neither a `Receive` the agent waits in nor the server's call: nothing happens within 2 s, with `net/http`'s and with `x/net/http2`'s transport. Only the next stream call carries it, and then the server reads a clean EOF, indistinguishable from a graceful end. Server errors and clean ends reach the client | **no** |
| 3 Deadlines | `grpc-timeout` carries the deadline (server within 5 ms of the client). On a stream, an expired deadline ends neither a waiting `Receive` nor a handler waiting in `Receive`, although both call contexts have expired. Unary deadlines work | **no** |
| 4 Message-size limits (4 MiB) | Without compression all six cases pass: 4 MiB accepted, 4 MiB + 1 refused by the sender's and by the receiver's limit, both directions. But when the client's read limit refuses a message on a stream the server keeps open, `Receive` blocks until the stream is closed. gzip, on by default, makes the sender count the compressed size | **no** |
| 5 HTTP/2 PING liveness, 20 s / 10 s | Blackholed path: client and server close 30 s after the last frame (20 s read idle + 10 s ping timeout), directly and through a TLS passthrough; a healthy idle session survives (scaled: 15 intervals) | yes |
| 6 10 000 idle sessions | Controller: 71 KiB heap and stacks per session (76 KiB RSS), 3 goroutines; agent: 81 KiB (100 KiB RSS), 2 goroutines; about 11 % of one core on each side for the 20 s pings. Set up in 6 s | yes (recorded) |
| 7 Behind a TLS-passthrough route | SNI-only routing; mutual TLS terminates at the controller; the handler sees the agent's SPIFFE ID; a plaintext marker never appears at the relay; unknown SNI and non-TLS closed; liveness works through it | yes |
| TLS | Another CA's certificate, a controller certificate as client, no client certificate and TLS 1.2 are refused | yes |

The same failing cases with grpc-go (client and both server modes, and a grpc-go client against the
connect-go handler): a cancel ends the client's `Recv` and the server's call within 0.5 ms; an
expired deadline ends both within 1 ms; a read-limit error on an open stream returns at once and
resets the stream. grpc-go also counts the compressed size when sending. 10 000 idle grpc-go
sessions: controller 85 KiB (71 KiB RSS), agent 98 KiB (102 KiB RSS), about 10 % of one core.
Keepalive on a blackholed path: server (1 s / 0.5 s) 0.5 s, client (10 s / 1 s) 10 s.

Facts ([F] at the pinned versions):

- Go's HTTP/2 client reads a streaming request body without watching the request context
  [F Go 1.27.1 `net/http/internal/http2/transport.go:1672`]
  [F x/net v0.59.0 `http2/transport.go:1521`]; the context is checked only after the body ends
  [F Go 1.27.1 `net/http/internal/http2/transport.go:1355-1370`]. connect-go leaves cancellation to
  the transport and watches the context only until the response arrives
  [F connect v1.21.0 `duplex_http_call.go:297-310`]. Two such hangs are open Go issues
  (golang/go#48908, #43989).
- After a receive error, connect-go's gRPC client reads the response body to its end to get the
  trailers [F connect v1.21.0 `protocol_grpc.go:319-321,368-377`].
- connect-go checks `sendMaxBytes` after compression [F connect v1.21.0 `envelope.go:158-178`] and
  enables gzip by default on handlers and clients
  [F connect v1.21.0 `handler.go:383`, `client.go:339`]. A lost connection reaches the client as
  `invalid_argument` ("incomplete envelope") [F connect v1.21.0 `envelope.go:338`], not
  `unavailable`.
- `net/http` configures HTTP/2 PINGs with `HTTP2Config.SendPingTimeout` (the read-idle timeout) and
  `PingTimeout` on `http.Server` and `http.Transport` [F Go 1.27.1 `net/http/http.go:299-307`];
  both ends implement them [F Go 1.27.1 `net/http/internal/http2/server.go:807-810,905-930`]
  [F Go 1.27.1 `net/http/internal/http2/transport.go:631-632,707-720,2041-2049`]. No `x/net`
  dependency is needed for that.
- grpc-go's default enforcement `MinTime` is 5 minutes
  [F grpc v1.84.0 `internal/transport/defaults.go:40`, `keepalive/keepalive.go:94`]; client
  keepalive below 10 s is raised to 10 s [F grpc v1.84.0 `dialoptions.go:576-578`];
  `grpc.Server.ServeHTTP` is experimental and lacks parts of grpc-go's own HTTP/2 server, among them
  keepalive enforcement [F grpc v1.84.0 `server.go:1132-1140`].
- buf's STANDARD lint rejects the sketch's names (`service Control`, `AgentMessage`,
  `ControllerMessage`); the spike added exceptions.

## Outcome

Checks 2, 3 and 4 fail, so the rule applies: **grpc-go carries the agent protocol**; browsers and
the CLI stay on ConnectRPC, and the protobuf contract does not change. A workaround exists (close
the response side when the context ends, which ends both sides within about 1 ms), but the rule
asks whether ConnectRPC carries the session as it is, and it does not.

[ADR-0016](../adr/0016-connectrpc-public-api-grpc-go-agents.md) records the applied fallback and is
**Accepted**; [ADR-0010](../adr/0010-connectrpc.md) is **superseded**. ADR-0016 also settles what
the fallback needs: grpc-go's own server (not `ServeHTTP`) with the enforcement policy of
[03](../03-connections.md#timeouts-keepalive-and-backoff), the controller's TCP/443 split by SNI
between that server and `net/http`, and no compression on the control session.

Changed in the same PR: ADR-0010, ADR-0016, [02](../02-architecture.md),
[03](../03-connections.md#control-session), [07](../07-api.md), [08](../08-software-stack.md), and
the links in ADR-0006 and ADR-0014.

## Not verified

- The controller's SNI split on TCP/443 between grpc-go and `net/http`: not built; it uses the
  ClientHello peek that S3 tests for the gateway.
- `Enroll` without a client certificate on the grpc-go server (certificate requested, not
  required; every other method checked by the interceptor): not prototyped.
- grpc-go keepalive at the real values (20 s / 10 s): only scaled values ran. grpc-go's identity
  check behind the passthrough: the relay is byte-transparent, but only connect-go was checked
  there.
- Real networks with latency and loss; all runs used loopback on one machine.
- The connect-go findings were not reported upstream.
