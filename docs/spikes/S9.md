# S9: How do controller replicas share session ownership?

Status: Done · Date: 2026-10-19 · Issue: #595 · Code: tag `spike/s9`
(branch `tmp/s9-controller-ha` while running)

## Question and rule

- **Method** ([13](../13-roadmap.md#phase-0--spikes)): PostgreSQL `LISTEN/NOTIFY` for the session
  registry and push fan-out; controller-to-controller mutual TLS for imperative operations;
  revocation-log shipping to the shared sink with conditional-create sequencing; a replica killed
  under load. Issue #595 split it into five questions:
  - **Q1** push fan-out: 3 replicas, 1 000 agents, a push reaches the agent within 1 s of commit
    at p99; no push lost when the LISTEN connection drops;
  - **Q2** the session registry under supersede and reconnect storms: exactly one session per
    agent;
  - **Q3** `ProbeTarget` forwarded over controller-to-controller mutual TLS below the probe timeout;
  - **Q4** two revocation-log shippers racing on MinIO and on a filesystem: no gap, no duplicate;
  - **Q5** a replica killed with SIGKILL under load: no dropped data connection; control failover
    within the reconnect backoff.
- **Pass criteria:** an agent's push reaches it within 1 s of commit; failover within the
  reconnect backoff.
- **Rule:** if `LISTEN/NOTIFY` is insufficient, push fan-out goes over controller-to-controller
  mutual TLS. Sub-rules ([D112](../14-open-decisions.md#project-and-process)): notifications lost
  while a replica reconnects cause a full resync, and the revision check of
  [03](../03-connections.md#timeouts-keepalive-and-backoff) stays as the safety net; PgBouncer in
  transaction mode is unsupported; if MinIO fails conditional create, the S3-compatible sink waits
  and the filesystem sink stays the requirement for several replicas.

## Setup

- Development machine (x86-64, Linux 6.18 under WSL2, 20 CPUs), shared with other builds during
  some runs: latencies are indications, not targets.
- Go 1.27.2; PostgreSQL 18.6 and pgx v5.11.0; MinIO `RELEASE.2025-10-15T17-29-55Z`, built from
  source because the project is archived and its images and binaries are no longer published
  (checked 2026-10-19); aws-sdk-go-v2 `service/s3` v1.114.3 as the spike's S3 client.
- One binary: each question starts three replicas as separate processes against one database and
  simulates the agents, with rpmgr's reconnect backoff and admission limit (03). A revision is a
  broadcast signal; a change of one agent's snapshot is a signal on the channel of the replica
  that holds it. The filesystem sink is the product's `internal/revlog`; the S3 sink uses its
  algorithm with `If-None-Match: *`.
- Data connections across a controller SIGKILL ran with the product: the nightly chaos cell of
  `test/e2e` with a seed whose first five controller events are all SIGKILL.
- Code, commands and raw results: `spikes/s9/` on the tag, with a `README.md` for every run.

**Facts re-checked at the pinned versions (D39):**

- A payload must be shorter than 8 000 bytes: 7 999 bytes are delivered, 8 000 are refused with
  `payload string too long` [F PostgreSQL 18.6 `src/backend/commands/async.c:163,619-622`].
- Notifications are queued at commit and delivered in commit order; a rolled-back transaction
  sends none; identical notifications of one transaction are sent once
  [F PostgreSQL 18.6 `async.c:52-56,907-922`]. All four were observed.
- A session receives only notifications committed after its `LISTEN`; those committed while it is
  disconnected are lost to it [F PostgreSQL 18.6 `async.c:1066-1121`] [F PostgreSQL 18 docs,
  LISTEN, Notes, retrieved 2026-10-19]. A listener inside a transaction receives nothing until it
  ends. Observed.
- Transactions that `NOTIFY` commit one at a time: a lock on "database 0" is held from the queue
  insert to the end of the commit [F PostgreSQL 18.6 `async.c:907-922`]. With 8 writers on
  distinct rows, 2 026 commits/s without and 692 with a `NOTIFY` on this machine.
- `max_notify_queue_pages` is 1 048 576 pages (8 GiB) [F PostgreSQL 18.6 `async.c:428`].
- PgBouncer never supports `LISTEN` in transaction pooling [F PgBouncer 1.26 docs, features,
  retrieved 2026-10-19].
- MinIO evaluates `If-None-Match: *` under the object's namespace lock and answers 412
  [F MinIO RELEASE.2025-10-15T17-29-55Z `cmd/erasure-object.go:1261-1281`,
  `cmd/object-handlers-common.go:182-193,345-348`]; Amazon S3 documents the same 412
  [F Amazon S3 user guide, conditional writes, retrieved 2026-10-19].

## Outcome

`LISTEN/NOTIFY` is sufficient: the rule's fallback, fan-out over controller-to-controller mutual
TLS, is not taken. The sub-rules of D112 apply as agreed; MinIO passed conditional create, so the
S3-compatible sink does not wait. The design the spike ran, now in
[10](../10-operations.md#high-availability):

- Registration takes the next `session_epoch` under the registry row's lock and, in the same
  transaction, signals the replica that held the agent before, which ends that session, also when
  the signal arrives before it has added the session. A targeted signal reads the registry row
  `FOR SHARE`, so it reaches the replica that registers the agent at the same time.
- A dedicated connection, never in a transaction, `LISTEN`s first and then resyncs every session
  it holds, on start and after each reconnect. The 1 s revision check also ends sessions whose
  registry epoch moved on.
- Notifying transactions stay short, because they commit one at a time.

[ADR-0011](../adr/0011-sqlite-postgres-ent-atlas.md#verification) records the result; 10 and 13
are updated. Slices 9.1–9.6 build on it.

## Not verified

- Replicas on separate hosts: every process ran on one machine, so a killed replica's connections
  ended at once. A lost host is noticed through the control keepalive of 03 (up to 30 s) before
  the backoff starts.
- A PostgreSQL failover or restart, and a managed PostgreSQL service.
- The filesystem sink on NFS or SMB: only tmpfs and ext4 ran.
- S3 services other than MinIO, and MinIO with several drives; MinIO has no maintained release.
- PgBouncer itself: the sub-rule rests on its documentation.
- The 4.35 s supersede outlier of one Q2 run was not explained; it did not recur.
