# S2: Does reverse HTTP/2 give full-duplex streams with half-close and reset semantics?

Status: Done · Date: 2026-10-06 · Issue: #6 · Code: tag `spike/s2` (branch `tmp/s2-reverse-h2`
while running)

## Question and rule

From [13](../13-roadmap.md#phase-0--spikes): the connector as HTTP/2 server on a connection it
dialled; 1 GiB in both directions concurrently; half-close each side; abort mid-stream; the
gateway-opened session control stream and `OpenRequest`-driven streams; tuned windows and stream
limits on a client connection over an existing connection; behaviour at the stream limit; stall
detection under connection-window pressure; how much of the extra round trip a first chunk in
`OpenRequest` hides. Pass: correct bytes, FIN and RST mapping in all cases; no deadlock under
flow-control pressure; never blocks at the stream limit. Decides
[ADR-0005](../adr/0005-reverse-http2-fallback.md).

Rule, agreed before the run: pass → reverse HTTP/2 as designed; fail → a patched yamux.

## Setup

- Go 1.27.1 (linux/amd64), `golang.org/x/net` v0.59.0 (its `go.mod` requires Go 1.26); WSL2
  kernel 6.18, 20 cores shared with other spikes running at the same time, so throughput and memory
  figures are indicative. The facts below were read at these versions (D39).
- `spikes/s2/` on the tag `spike/s2`: a connector that serves HTTP/2 on the TLS 1.3 mutual-TLS
  connection it dialled (ALPN `rpmgr-tunnel-h2/1`, test CA, SPIFFE checks), a gateway that opens
  every stream, a stall-detection prototype, one test per criterion and `run.sh`; the RTT is
  injected by a user-space delay proxy, not netem. `./run.sh criteria|legacy|race|measure`
  repeats every run; the raw output is in `results/`.
- Three HTTP/2 implementations: **`stdlib`**, net/http's own HTTP/2 in Go 1.27 (`http.Server`,
  `http.Transport.NewClientConn`, `http.HTTP2Config`); **x/net** v0.59.0 (`http2.Server.ServeConn`,
  `http2.Transport.NewClientConn`), which with Go 1.27 is a wrapper around net/http's code; and
  **x/net legacy**, x/net's own code (`-tags http2legacy`).
- Two half-close mappings: **as designed**, where the connector's FIN ends the HTTP response; and
  **in-band FIN**, where the connector-to-gateway bytes after `StreamResult` are chunks of
  `varint(length) ‖ bytes`, a zero-length chunk is the connector's FIN, and the response ends only
  when both directions have.

## Results

All tests pass on all three implementations, also under `-race`; the as-designed half-close fails
as recorded below.

| Criterion | Result | Pass |
|---|---|---|
| 1 GiB in both directions at once | SHA-256 equal at both ends, every implementation and mapping; 43–138 MiB/s per direction on the shared host | yes |
| Half-close, gateway first | The request's `END_STREAM` reaches the connector as EOF; the connector then sends 4 MiB, all delivered | yes |
| Half-close, connector first, as designed | Ending the response makes net/http's server reset the request with `RST_STREAM(NO_ERROR)`: the gateway's next write fails, the connector receives 0 of 4 MiB. Same in all three implementations | **no** |
| Half-close, connector first, in-band FIN | The zero-length chunk reaches the gateway as EOF; the gateway then sends 4 MiB, all delivered | yes |
| Abort mid-stream | A reset by either side reaches all four ends as an error, never as EOF, within 2 ms | yes |
| Control stream first; `OpenRequest` | The first request is the control stream, a stream before it is refused (421); `OpenRequest` gets a stream with `open_id` and result and no `StreamResult`; `OpenRejected`; a duplicate `open_id` is refused (`PROTOCOL`); unanswered requests time out after 300 ms and after 10 s; a late stream for a timed-out `open_id` is reset | yes |
| No deadlock under flow-control pressure | 4 streams the gateway does not read and 4 the connector does not read (64 MiB each way): new streams and the control stream keep working (Ping 0.3–0.9 ms) | yes |
| Stall detection | 17 stalled streams fill the 256 MiB connection window: new streams and the flow-controlled `Ping` stop, HTTP/2 PING keeps the session alive; the prototype resets the 9 oldest and traffic resumes. One paused stream without pressure is never reset | yes |
| Never blocks at the stream limit | At the limit the gateway's reservation fails at once (< 50 ms) and it uses another session; 9 999 concurrent streams plus the control stream on one session, the next one refused at once | yes |
| Windows on a client connection over an existing connection | Unread bytes in flight per stream: 16 MiB in both directions with the rpmgr values, 4 MiB (to the gateway) and 1 MiB (to the connector) with the defaults; 255–256 MiB per connection | yes |
| HTTP/2 PING liveness | A blackholed connection is detected by both ends after 25.0 s (`SendPingTimeout` 15 s + `PingTimeout` 10 s) | yes |

Cost of `OpenRequest` (median of 15, `stdlib`; x/net within 0.6 ms). The far end answers the
first chunk at once, so the time to the first answer shows every round trip:

| RTT | Gateway-opened stream | `OpenRequest`, no first chunk | `OpenRequest` with first chunk |
|---|---|---|---|
| 20 ms | 21.7 ms | 42.8 ms | 21.8 ms |
| 80 ms | 81.9 ms | 163.1 ms | 82.0 ms |

Single stream at 100 ms RTT (`stdlib`): default windows 80 Mbit/s towards the connector and
328 Mbit/s towards the gateway (03 computes 84 and 335); rpmgr windows 1 251 and 1 327 Mbit/s
(ceiling 1 342).

Findings ([F] at Go 1.27.1 and x/net v0.59.0):

- Go 1.27's net/http has the APIs the design needs. `golang.org/x/net/http2` is now a deprecated
  wrapper around it unless built with `http2legacy`
  [F x/net v0.59.0 `http2/transport_wrap.go:5`, `http2/transport_common.go:298-303`], and its
  `Transport` passes no receive windows [F x/net v0.59.0 `http2/transport_wrap.go:73-84`].
- Client windows over an existing connection: an `http.Transport` with only unencrypted HTTP/2
  enabled, a `DialContext` that returns the accepted connection and `HTTP2` set, then
  `NewClientConn(ctx, "http", …)` [F Go 1.27.1 `net/http/clientconn.go:113`]. The documentation
  says the receive buffers must be "less than 4MiB" [F Go 1.27.1 `net/http/http.go:289,295`];
  the code accepts up to 2³¹ − 1 [F Go 1.27.1 `net/http/internal/http2/config.go:55-62`], and the
  tuned windows were measured in force.
- The half-close limit is deliberate: the server resets the request because "net/http provides no
  mechanism for closing a ResponseWriter while still reading data"
  [F Go 1.27.1 `net/http/internal/http2/server.go:1207-1224`]; x/net's own server does the same.
- Defaults re-checked: 250 streams [F Go 1.27.1 `net/http/internal/http2/server.go:61`]
  [F x/net v0.59.0 `http2/server.go:62`]; server buffers 1 MiB per stream and per connection
  [F Go 1.27.1 `net/http/internal/http2/config.go:55,60`]
  [F x/net v0.59.0 `http2/config.go:105,110`]; client 4 MiB per stream and 1 GiB per connection
  [F Go 1.27.1 `net/http/internal/http2/transport.go:45,50`]
  [F x/net v0.59.0 `http2/transport.go:43,48`]; PING settings `SendPingTimeout` and `PingTimeout`
  [F Go 1.27.1 `net/http/http.go:302,307`].
- `ClientConn.RoundTrip` waits at the concurrency limit; `Reserve` fails instead
  [F Go 1.27.1 `net/http/clientconn.go:254,301`].
- A reset stream's unread bytes keep holding connection window on the client until the response
  body is closed [F Go 1.27.1 `net/http/internal/http2/transport.go:2402-2421`]; the server returns
  them when the stream closes [F Go 1.27.1 `net/http/internal/http2/server.go:1576-1579`]. The first
  prototype reset by cancellation alone and never got the window back.
- Neither side exposes how many bytes a stream holds unread, so the stall rule counts a stalled
  stream at its full receive window, an upper bound: it fires at most early.
- Memory: the client's request-body buffer is min(the peer's `SETTINGS_MAX_FRAME_SIZE`, 512 KiB)
  [F Go 1.27.1 `net/http/internal/http2/transport.go:1607-1620`], and net/http advertises 1 MiB
  by default [F Go 1.27.1 `net/http/internal/http2/http2.go:82`]: 559 KiB per open stream. With
  16 KiB frames, 62 KiB per stream for both ends together, of which 32 KiB are the prototype's
  buffers; goroutine stacks add about 16 KiB.

## Outcome

The design as written fails one criterion — the connector's FIN — in every Go HTTP/2
implementation, so the pre-agreed rule selects **a patched yamux**. The spike also shows that
reverse HTTP/2 passes **every** criterion when the connector's FIN travels in-band. The rule did not
foresee that variant, so the choice is the product owner's, recorded in
[14](../14-open-decisions.md):

- **(a) Apply the rule:** a patched yamux (half-close, `Read` after local close, larger windows)
  as a separate module behind `internal/tunnel`; ADR-0005 superseded. Not prototyped.
- **(b) Reverse HTTP/2 with an in-band connector FIN** (recommended): standard library only, no
  fork to maintain, every criterion measured; costs 1–3 bytes per chunk of up to 16 KiB in one
  direction of the TCP transport. ADR-0005 accepted with that change, net/http instead of
  `x/net/http2`, and 16 KiB frames.

Until the decision, ADR-0005 stays *Proposed*; its Verification section records this result.

## Not verified

- The rule's fallback, a patched yamux, was not prototyped.
- Loss and real kernel TCP behaviour: the RTT came from a user-space proxy; loss is S1's.
- WSS wrapping (Phase 2), HTTP CONNECT and SOCKS5 proxies, and two TCP connections per gateway.
- Admission of h2 sessions against the process-wide window budget ([03](../03-connections.md)).
- The stall rule at its real age of 30 s (scaled to 100–300 ms in the tests).
